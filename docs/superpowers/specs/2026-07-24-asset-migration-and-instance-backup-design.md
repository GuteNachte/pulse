# Pulse 资产迁移与完整实例备份设计

日期：2026-07-24

状态：已确认设计，等待实施计划

## 1. 背景

Pulse 当前已经有两套相关能力：

- 资产中心可以导出筛选后的 CSV，也可以导出包含资产、接口、关系、位置、维护记录和附件索引的 JSON 快照。
- 设置页可以调用 PocketBase 原生备份接口，创建、下载、还原和删除 Hub 备份。

现状仍不能满足可靠迁移：

- JSON 快照只能留档，当前导入流程只会创建资产主记录，不能恢复接口、关系、位置、维护、附件和设备图片。
- 资产附件和设备图片只导出索引，文件本身没有进入资产迁移包。
- PocketBase 原生备份会包含默认 `pulse_data` 下的数据，但无法保证包含配置到数据目录外的设备图片目录。
- 资产编号规则保存在浏览器 `localStorage`，不会进入 Hub 备份。
- 新 Hub 没有上传本地备份、兼容性预检和恢复后核验流程。

本设计将迁移能力拆成两个互补层级：

1. 资产迁移包：用于选择性迁移资产中心主数据。
2. 完整实例备份：用于开发环境迁移到正式部署，保留整个 Pulse 实例。

## 2. 目标

- 资产可以在两个 Pulse 实例之间迁移，接口、关系、位置、附件和图片保持正确关联。
- 完整实例迁移后保留管理员账号、用户、设置、模块状态、资产、拓扑、监控、告警、审计和文件。
- 正式部署可通过“创建并下载备份 -> 上传到新 Hub -> 预检 -> 还原”完成。
- 所有导入和还原在修改数据前完成校验，失败后不留下半成品数据。
- 包格式带显式版本、记录数量和 SHA256，可识别损坏、不兼容和不可信输入。
- UI 延续 Pulse 紧凑、简约和高信息密度的现有设计语言。
- `pulse_data` 始终作为正式部署的持久数据目录，更新镜像不得删除或重建该目录。

## 3. 非目标

- 不迁移浏览器登录会话、当前筛选、滚动位置、移动端缓存等临时状态。
- 不把资产迁移包当作监控历史、账号或完整系统设置的备份。
- 第一版不提供云端备份调度、异地同步、增量备份或备份密码加密。
- 第一版不支持从高于当前 Hub 的包格式或数据库版本降级恢复。
- 不在前端直接重建跨集合数据；复杂导入和还原统一由 Hub 负责。

## 4. 模块归属

### 4.1 资产迁移包

归属 `asset-center` 模块。前端代码进入 `internal/site/src/modules/asset-center`，Hub 端导入导出逻辑进入资产中心对应模块边界。资产页面只负责触发、展示预检和反馈。

### 4.2 完整实例备份

归属 `maintenance` 模块。现有 `settings-backups` 页面保留为入口，Hub 备份 API 向 maintenance 边界收敛。PocketBase 原生备份继续作为数据库与默认数据目录的底层能力。

### 4.3 长期设置

资产编号规则归属 `asset-center`，从浏览器 `localStorage` 迁入当前用户的 `user_settings`。主题、语言、当前筛选和缓存仍属于浏览器偏好，不进入业务备份。

## 5. 方案选择

### 5.1 已采用：双层迁移

- 资产迁移包解决选择性迁移、人工盘点和跨实例合并。
- 完整实例备份解决正式部署、灾难恢复和全量状态保留。
- 两层使用不同格式和恢复语义，避免用户误把资产 JSON 当成整机备份。

### 5.2 未采用：只做完整实例备份

实现较简单，但无法选择性导入资产，也无法安全合并两个实例的资产中心数据。

### 5.3 未采用：只做资产迁移包

不能保留账号、系统设置、拓扑布局、监控历史、告警、审计和其他模块数据，不符合正式部署后“所有数据都还在”的目标。

## 6. 资产迁移包

### 6.1 文件格式

文件名：`pulse-assets-<YYYYMMDD-HHMMSS>.pulse-assets.zip`

ZIP 根目录固定包含：

```text
manifest.json
records.json
files/
  attachments/
  media/
```

`manifest.json` 至少包含：

```json
{
  "schema": "pulse.asset-center.package.v1",
  "package_id": "稳定的随机 ID",
  "pulse_version": "1.0.6",
  "created_at": "ISO-8601",
  "source_instance": "不含秘密的实例 ID",
  "scope": "asset-center",
  "counts": {},
  "files": [
    {
      "path": "files/...",
      "size": 0,
      "sha256": "..."
    }
  ]
}
```

`records.json` 包含资产中心拥有的长期数据：

- `asset_locations`
- `assets`
- `asset_interfaces`
- `asset_relations`
- `asset_maintenance`
- `asset_attachments`
- `asset_visuals`
- `asset_media`
- `asset_media_versions`
- `asset_media_placements`
- 已完成的资产补全报告与建议

资产迁移包不包含 `systems`、`website_monitors`、监控历史、账号、Token、审计或 AI 临时任务。这些只由完整实例备份负责。

导出集合由资产中心后端 registry 声明，不在页面中分散硬编码。以后资产中心增加新的长期子档案时，registry 和包格式测试必须同步更新。

### 6.2 文件处理

- `asset_attachments` 对应的 PocketBase 文件复制到 `files/attachments`。
- 本地设备图库的原图、派生版本和当前展示版本复制到 `files/media`。
- 远程候选图片 URL 只保留记录；已经进入本地图库的图片必须包含实际文件。
- 每个文件都在 manifest 中记录相对路径、大小和 SHA256。
- ZIP 内禁止绝对路径、`..` 路径和符号链接。

### 6.3 导入预检

上传后先解压到 Hub 管理的临时目录，只有预检通过才能确认导入。预检返回：

- 包格式和 Pulse 版本。
- 每类记录与文件数量。
- SHA256 与缺失文件结果。
- 目标实例中的重复资产和可能冲突。
- 孤立位置、接口、关系、附件和图片引用。
- 预计新增、合并、跳过和覆盖数量。
- 总体状态：`ready`、`warning` 或 `blocked`。

旧格式包通过显式升级器转换到当前内存模型；新于当前 Hub 的格式返回 `blocked`，不得猜测导入。

### 6.4 冲突策略

导入提供三个互斥模式，使用紧凑分段控件选择：

- `add_only`：默认。只创建不存在的数据，重复资产及其已存在子档案跳过。
- `merge`：匹配到现有资产时只填充空字段，不覆盖目标实例已有非空值；缺失子档案补建。
- `replace_matched`：用包内容更新匹配资产及包内包含的子档案，但不删除包外无关资产。

匹配优先级固定为：

1. 同一迁移来源的原始记录 ID。
2. 非空且唯一的资产编号 `asset_tag`。
3. 非空序列号，且厂商和型号一致。

管理 IP、名称和 MAC 只作为冲突提示，不能单独作为覆盖身份依据。

### 6.5 恢复顺序与 ID 映射

Hub 建立 `source ID -> target ID` 映射，按以下顺序写入：

1. 位置。
2. 资产。
3. 网卡和接口。
4. 资产关系。
5. 维护记录和附件。
6. 设备图片、图片版本和展示位置。
7. 资产补全报告与建议。

父位置、父资产、接口端点、关系端点、附件资产和图片资产全部通过映射重写。任何无法解析的必需引用都会阻止导入，不允许生成悬空记录。

### 6.6 原子性

- 数据库写入在 Hub 事务内执行。
- 文件先写入临时目录，校验成功后再移动到目标目录。
- 数据库失败时删除本次临时文件。
- 文件提交失败时回滚数据库事务。
- 导入完成前不刷新资产列表，也不广播“导入成功”。

## 7. 完整实例备份

### 7.1 文件格式

文件名：`pulse-instance-<YYYYMMDD-HHMMSS>.pulse-backup.zip`

外层包固定包含：

```text
manifest.json
pocketbase.zip
external/
  asset_media/
```

- `pocketbase.zip` 由当前 PocketBase `CreateBackup` 生成，负责数据库、默认文件存储和 `pulse_data` 内数据。
- `external/asset_media` 仅在设备图片目录配置到 `pulse_data` 外时存在。
- manifest 记录 Pulse、PocketBase、数据库 schema、包格式、文件校验、数据范围和来源实例。
- 现有 PocketBase 原生 `.zip` 继续显示为“旧版原生备份”，保持下载和还原兼容，但不声称包含外置图片或 Pulse 校验清单。

### 7.2 数据范围

完整实例备份包含：

- 管理员和普通用户账号。
- PocketBase 与 Pulse 系统设置。
- `user_settings` 和 `module_settings`。
- 资产中心全部数据和文件。
- 网络拓扑布局。
- 机器、网站监控、历史指标和采集数据。
- 告警、通知配置、Agent Token、配对凭据和 AI 密钥。
- 系统日志和操作审计中持久化到数据库的记录。
- 默认 `pulse_data` 下的 PocketBase storage、设备图片和其他运行所需持久文件。

不包含：

- 浏览器认证存储和当前登录会话。
- 前端缓存、当前筛选、滚动位置和临时上传目录。
- `backups` 目录中的其他历史备份，避免递归打包。

### 7.3 上传与预检

新 Hub 的管理员可以从设置页上传 `.pulse-backup.zip`。上传采用流式写入和大小限制，不把整个文件读入内存。

预检必须确认：

- ZIP 与 manifest 结构合法。
- 所有文件大小和 SHA256 匹配。
- 备份 Pulse 版本不高于当前 Hub。
- 数据库 schema 存在明确升级路径。
- PocketBase 内层备份可读取。
- 目标数据目录和目标设备图片目录可写。
- 磁盘可用空间足够容纳解压、恢复和自动安全备份。

对于外置设备图片，预检页显示来源存储模式并要求选择目标目录。默认恢复到目标 Hub 的 `pulse_data/asset_media`，不直接复用来源机器的绝对路径。

### 7.4 恢复保护

- 上传、预检和恢复只允许管理员执行。
- 恢复前自动创建当前目标实例的安全备份。
- 用户必须完成危险操作确认，界面明确说明账号、Token、设置和业务数据都会被替换。
- 还原以后台恢复任务执行，返回任务 ID，页面显示阶段和最后错误。
- PocketBase 数据恢复后，Hub 启动阶段继续完成外置文件恢复、目标路径设置和最终核验。
- 恢复成功后当前浏览器会失去原目标实例会话，页面提示使用备份中的管理员账号重新登录。
- 恢复失败时优先自动回到恢复前安全备份；自动回退失败时停止启动并输出明确的人工恢复路径。

### 7.5 恢复后核验

Hub 启动后执行一次恢复核验：

- 数据库可打开且迁移完成。
- 管理员账号至少保留一个。
- manifest 声明的核心集合存在。
- 资产、接口、关系、位置和文件数量与包内清单一致。
- 不存在悬空资产关系和缺失文件。
- 设备图片存储目录可读写。
- `/api/health` 恢复正常。

核验结果写入恢复任务和操作审计。只有核验通过才显示“恢复成功”。

## 8. 资产编号设置迁移

- 新增资产中心用户设置键，保存 `prefix`、`digits` 和 `nextSequence`。
- 首次读取时，如果服务器没有该设置但浏览器存在旧 `pulse.asset-center.numbering`，前端一次性迁移到 `user_settings`。
- 服务器保存成功后再删除旧本地值；失败时继续使用本地值，避免设置丢失。
- 后续读取以服务器为准，使同一账号在新实例恢复后继续使用原编号规则。

## 9. 前端交互

### 9.1 资产导出

现有“导出资产”弹窗保留两个主要动作：

- 当前清单 CSV。
- 资产迁移包。

旧的“完整主数据 JSON”改为迁移包，不再用“完整”描述一个不能恢复文件的索引快照。导出期间按钮显示进度并禁止重复提交。

### 9.2 资产导入

导入弹窗自动识别：

- CSV：继续走批量建档预览。
- 旧 JSON / 对象数组：继续走兼容导入，只处理资产主档。
- `.pulse-assets.zip`：进入迁移包预检、模式选择和确认流程。

预检摘要用紧凑表格展示记录范围、文件、冲突和阻止项。页面不新增大型步骤导航；只在同一弹窗内按“选择文件 -> 预检 -> 确认结果”切换内容。

### 9.3 设置页备份管理

现有设置页增加“上传备份”按钮，备份表格增加：

- 类型：Pulse 完整备份或旧版原生备份。
- Pulse 版本。
- 校验状态。
- 数据范围摘要。
- 大小和创建时间。

创建、下载、预检、还原和删除继续使用现有按钮、图标、表格和确认弹窗样式。桌面端优先紧凑布局，本次不新增移动端专属设计，但不得破坏已有移动端入口。

## 10. API 边界

建议新增或收敛以下 Hub API：

```text
POST   /api/pulse/assets/migrations/export
POST   /api/pulse/assets/migrations/upload
POST   /api/pulse/assets/migrations/{id}/preflight
POST   /api/pulse/assets/migrations/{id}/apply
GET    /api/pulse/assets/migrations/{id}

POST   /api/pulse/backups
POST   /api/pulse/backups/upload
POST   /api/pulse/backups/{key}/preflight
POST   /api/pulse/backups/{key}/restore
GET    /api/pulse/backups/tasks/{id}
GET    /api/pulse/backups/{key}
DELETE /api/pulse/backups/{key}
```

资产迁移 API 受 `asset-center` 模块和当前用户数据范围约束；完整备份 API 受 `maintenance` 模块和管理员角色约束。

上传接口使用服务端生成的临时 ID，不信任客户端文件名。所有临时文件设置过期时间，并在成功、取消或超时后清理。

## 11. 安全与审计

- 完整实例备份含密码哈希、Agent Token、配对凭据、通知秘密和 AI 密钥，下载和还原页面必须明确提示敏感性。
- 第一版包不内置加密；文档要求只存放在可信位置，对外传输前使用受信任的加密容器。
- 所有 ZIP 读取防止路径穿越、符号链接、异常文件数量和压缩炸弹。
- 上传设置总大小、单文件大小、条目数量和解压后总大小上限。
- 完整备份文件只允许管理员列出和下载。
- 操作审计记录创建、上传、预检、下载、删除、导入、恢复、自动安全备份、恢复核验和失败原因。
- 审计详情不记录 Token、密钥、文件内容或完整 manifest 中的敏感字段。

## 12. 错误处理

前端错误按阶段展示，不使用统一的“失败”覆盖真实原因：

- 上传失败：网络中断、大小超限或权限不足。
- 预检失败：包损坏、版本不兼容、校验失败、引用错误或空间不足。
- 导入失败：数据库约束、文件提交或事务回滚失败。
- 恢复失败：安全备份失败、PocketBase 恢复失败、外置文件恢复失败、启动核验失败或自动回退失败。

用户能看到可执行的下一步：重新上传、修复包、升级 Hub、释放空间、修改目标目录或使用安全备份人工恢复。

- 默认和外置设备图片目录。
- 旧 PocketBase 原生备份兼容。

### 13.3 端到端恢复演练

必须执行一次真实的临时实例演练：

1. 从当前开发 Hub 创建完整实例备份。
2. 启动使用全新空数据目录的临时 Hub。
3. 创建临时管理员并上传备份。
4. 完成预检和恢复。
5. 使用备份中的管理员重新登录。
6. 核对资产、接口、关系、位置、图片、拓扑、设置、监控和审计。
7. 验证 `/api/health`、前端构建和核心测试。

临时演练不得覆盖当前 `pulse_data`。

### 13.4 部署验收

- `supplemental/docker/hub/docker-compose.yml` 继续将 `./pulse_data` 挂载到 `/pulse_data`。
- `docker compose pull` 和 `up -d --force-recreate` 不删除 `pulse_data`。
- FlyNAS 正式部署前创建并下载一个完整实例备份，同时保留目录级 `tar` 备份作为第二恢复路径。
- 正式恢复完成后验证管理员登录、资产关系、设备图片、拓扑和 Agent 重连。

## 15. 完成定义

满足以下条件才视为完成：

- 资产迁移包可以在空实例中恢复全部资产中心长期数据和文件。

- 浏览器登录会话和临时缓存没有被打包。
- 外置设备图片被打包，并能选择目标存储目录恢复。
- 任何预检、导入或恢复失败都有明确状态、审计和回退路径。
- 相关前端测试、Go 测试、类型检查、构建和真实恢复演练通过。
