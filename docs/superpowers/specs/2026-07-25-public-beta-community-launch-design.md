# Pulse 公开测试与社区协作设计

## 状态与已确认决策

- Pulse 将完整开源，采用公开测试版方式首次对外发布。
- GitHub 是公开主仓库，GitHub Releases 发布安装产物，GHCR 发布公开容器镜像。
- 现有局域网 Gitea 继续作为私人镜像和备份，不对公网提供服务。
- 首个公开版本使用 `1.0.6-beta.1`，Hub、Agent、Web 和 Android App 保持同一个显式版本号。
- 宣传素材全部使用独立虚拟家庭数据，不使用当前家庭资产、网络、账号、日志、备份或设备图片。
- 中文是主要维护语言；英文完整覆盖 README、快速部署、贡献指南和 Issue 模板，并逐步扩展核心文档。

## 目标

1. 让不了解 Pulse 的用户能在三分钟内理解产品，并按文档完成首次部署。
2. 让测试者能提交可复现、已脱敏、包含必要环境信息的反馈。
3. 让外部开发者能快速建立开发环境、理解模块边界并提交可验证的 Pull Request。
4. 在不暴露私人基础设施和家庭数据的前提下，建立可持续的公开发布与社区协作流程。

## 非目标

- 首发阶段不承诺商业级响应时限、兼容范围或长期支持周期。
- 不公开现有 Gitea、Harbor、FlyNAS、家庭域名和真实运行数据。
- 不在应用内默认加入用户行为跟踪或遥测。
- 不为了宣传提前宣称尚未验证的设备、平台或采集能力。
- 首发阶段不同时建设大量社交账号和独立社区平台；交流统一收敛到 GitHub。

## 当前基础与缺口

当前仓库已经具备中文 README、MIT 许可证、`SECURITY.md`、发布与回滚手册、GitHub Issue / Discussion / PR 模板，以及质量检查、漏洞检查和议题维护工作流。公开前不重复建设这些能力，而是在现有基础上补齐以下缺口：

- 公开 GitHub 仓库和 GHCR / Releases 分发链路尚未建立。
- README 和部署文档仍包含面向私人 Harbor、局域网和本机环境的维护口径。
- 缺少面向外部贡献者的 `CONTRIBUTING.md`、行为准则、支持边界、模块导航和跨平台开发入口。
- 缺少虚拟演示数据、可复现截图、短视频、社交分享图和英文核心资料。
- `SECURITY.md` 尚未提供可用的私人安全报告渠道。
- 当前 `LICENSE` 保留上游版权，需要在合法保留上游声明的同时明确 Pulse 修改部分的版权和第三方归属。
- 需要对当前文件和完整 Git 历史执行敏感信息审计，不能只依赖人工查看最新版本。

## 公开发布架构

### 仓库与权限

- GitHub 公开仓库是外部协作的唯一主入口。
- `main` 开启分支保护，禁止直接写入；合并必须经过 Pull Request、必需检查和维护者审核。
- 外部贡献使用个人分支或 Fork，不提供生产环境、私人 Gitea、Harbor 和 FlyNAS 权限。
- Gitea 只从 GitHub 或本地受控流程同步，作为私人备份，不参与公开安装文档。

### 产物与版本

- GHCR 发布 Hub 和 Agent 的多架构镜像，使用显式版本，不发布可漂移的 `latest` 作为安装依据。
- GitHub Releases 发布版本说明、校验文件、Windows Agent、Android APK 和必要安装产物。
- `1.0.6-beta.1` 需要通过现有版本一致性、Go、Web、Android 和容器验证；发布脚本后续扩展为 GHCR / GitHub 目标，但私人 Harbor 发布能力保留为可选内部目标。
- 测试版和正式版使用清晰的升级、回滚与数据备份说明。

### 自动化和密钥

- 复用现有 `quality.yml` 和 `vulncheck.yml`，补充敏感信息、许可证、镜像、Release 产物和文档链接检查。
- GitHub Actions 使用最小权限和 GitHub Secrets / Environments；任何 Token、证书和密码不得写入代码、示例或工作流日志。
- 发布工作流只响应受保护标签或人工审批，不允许普通 Pull Request 获得发布凭据。

## 公开前安全与许可证审计

公开动作必须等待以下门槛全部通过：

1. 使用敏感信息扫描工具检查当前工作树、所有提交、标签和大文件。
2. 人工复核文档、截图、测试夹具、Compose、日志样例和发布脚本中的 IP、域名、邮箱、账号、Token 和本机路径。
3. 发现真实密钥时先吊销或轮换，再清理历史；不能只删除最新文件。
4. 发现历史隐私时使用受控历史重写，重新验证标签、分支和构建；没有敏感信息时保留完整历史和贡献记录。
5. 更新版权与第三方声明：合法保留上游 MIT 版权，明确 Pulse 新增修改的版权归属，并保持 `THIRD_PARTY_NOTICES.md` 与实际依赖一致。
6. `SECURITY.md` 改为 GitHub Private Vulnerability Reporting 或明确的私人联系入口。
7. 确认仓库不包含数据库、备份、日志、构建密钥、真实设备图片和家庭网络资料后，才允许创建公开仓库。

## 产品介绍、文档与演示素材

### 仓库首页

README 首屏依次展示产品名称、一句话定位、核心界面大图、版本 / 构建状态和三分钟启动入口。后续内容按目标用户、核心能力、实际限制、支持平台、架构、部署、升级、贡献和许可证排列，避免让用户先阅读内部维护文档。

中文 README 提供完整介绍，并提供明显的 English 入口。英文 README 保持相同的信息架构，至少完整覆盖定位、截图、快速部署、支持范围、反馈和贡献入口。

### 文档站

使用轻量静态文档站发布到 GitHub Pages，文档源文件与代码同仓库维护。内容分为：

- 快速开始、Docker Compose 部署和首次初始化。
- Windows、Linux、NAS / 飞牛和 Unraid Agent 接入。
- 资产中心、网络拓扑、监控、告警、智能家居和备份恢复。
- 升级、迁移、回滚、故障排查和数据位置。
- 隐私、安全、权限、支持边界和已知限制。
- 开发环境、模块架构、测试、贡献和发布规则。

### 虚拟演示数据

建立可重复生成的虚拟家庭：互联网入口、主网关、交换机、NAS、Windows 电脑、Linux 服务器、手机和智能家居设备。名称、序列号、IP、域名、MAC、图片和监控记录全部为虚构内容；域名使用 `example.com` 系列，任何值都不能从正式实例复制。

演示数据只用于本地演示、文档构建和截图，不进入普通用户首次启动的真实数据库。生成器必须可重复运行并支持清理。

### 图片与视频

- 使用 Playwright 从固定演示数据和固定桌面视口自动生成 6 至 8 张核心截图。
- 截图覆盖资产中心、资产详情、家庭网络、科技网拓扑、客户端监控、告警和备份恢复。
- 首发准备一段 30 至 60 秒 WebM / MP4 短视频，展示启动、进入首页、查看资产和打开拓扑的完整路径。
- 生成统一的 GitHub Social Preview 图片；图片不得包含真实账号、IP、域名或浏览器个人信息。
- 截图回归放入发布检查，避免文档长期展示过期界面。

## 测试反馈与贡献流程

### 反馈入口

- Issues 保留并完善 Bug 和功能建议表单，补充部署求助、设备兼容和文档问题分类。
- Bug 表单要求版本、操作系统、部署方式、复现步骤、预期 / 实际结果和脱敏日志。
- Discussions 负责公告、问答、功能想法、设备展示和使用案例，避免普通交流占用缺陷列表。
- 安全问题只走私人报告渠道。

### 外部开发者入口

- 新增 `CONTRIBUTING.md`、行为准则、支持政策、模块导航和 Pull Request 检查清单。
- 不引入高摩擦 CLA；贡献者提交代码即同意按项目许可证提供贡献，具体表述在贡献指南中写清楚。
- 为 Windows 保留一键启动，并为 Linux / macOS 提供等价开发命令和演示数据初始化方法。
- 网络拓扑、资产中心、Agent 和维护模块分别提供入口文件、数据源、测试命令和不可破坏边界。
- 建立 `good first issue`、`help wanted`、模块、难度、优先级和状态标签，并在公开前准备一批范围清楚的小任务。

### Pull Request 门槛

每个 Pull Request 至少检查 Go 测试与格式、前端测试、类型检查、生产构建、敏感信息、依赖漏洞、许可证和文档链接。涉及用户可见行为时必须更新测试、`docs/release-notes-next.md` 和 About 版本记录。涉及数据迁移、认证、备份或 Agent 协议时需要额外的端到端验证与回滚说明。

## 推广与社区运营

### 首发顺序

1. 完成安全、许可证、部署、演示和贡献门槛。
2. 发布 `1.0.6-beta.1`、GitHub Release、GHCR 镜像、文档站和演示素材。
3. 先在飞牛、NAS、Homelab、自托管和家庭网络相关中文社区发布完整介绍。
4. 使用英文 README 和相同演示素材发布到 GitHub、`r/selfhosted`、`r/homelab` 和 Show HN。
5. 安装体验稳定后再申请 Awesome Selfhosted 收录；首发阶段不把精力分散到过多平台。

所有宣传统一指向：

`项目介绍 -> 三分钟部署 -> Discussions 交流 -> Issue 反馈 -> Pull Request 贡献`

### 维护节奏

- 测试期每两周整理一次开发版更新，公开已修复、正在处理和需要帮助的事项。
- 不承诺商业级 SLA；README 和支持政策明确个人项目的响应边界。
- 默认不采集应用内遥测。效果只使用 GitHub 流量、Release 下载、GHCR 拉取、有效反馈和外部 PR 等公开统计。

## 成功指标

首发后 30 天以真实参与质量而非单纯 Star 数量判断：

- 至少 20 个真实环境成功部署。
- 至少 10 条可复现、可行动的有效反馈。
- 至少 3 个外部 Pull Request。
- 覆盖 Windows、Linux 和至少两类 NAS 环境。
- 建立一批愿意持续测试后续版本的早期用户。

## 优点、缺点与风险

### 优点

- 普通用户能快速判断项目是否适合自己并完成部署。
- 外部开发者获得明确边界、测试门槛和低摩擦贡献入口。
- 公开构建、版本和安全流程提高项目可信度与可持续性。
- 虚拟演示数据和自动截图降低长期文档维护成本。

### 缺点

- 中英文文档、截图、镜像、Issue 和版本需要持续维护。
- 测试期会增加问题分诊、兼容性确认和用户支持工作。
- GitHub 与私人 Gitea / Harbor 双目标需要保持发布口径一致。

### 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 历史提交泄露隐私或密钥 | 全历史扫描、人工复核、先轮换密钥、必要时受控重写历史 |
| 上游或第三方许可证不完整 | 保留上游版权、明确 Pulse 修改版权、维护第三方声明和自动检查 |
| 测试版缺陷影响第一印象 | 使用 beta 标识、明确限制、提供备份与回滚、先完成小范围部署验证 |
| 恶意代码或供应链风险 | 主分支保护、维护者审核、最小权限 CI、依赖与漏洞扫描 |
| 支持请求超出维护能力 | 统一入口、结构化模板、公开支持边界、按优先级和版本处理 |
| 演示素材意外包含真实信息 | 独立演示数据、自动生成、发布前敏感信息检查 |

## 实施顺序与授权边界

实施分为五个独立阶段：公开审计、公开分发、演示与文档、贡献协作、首发推广。每个阶段单独验证，前一阶段未通过不得进入下一阶段。

Codex 负责技术方案、任务拆分、代码、文档、检查和验证。以下动作必须由用户明确授权或提供账号权限后执行：

- 确定公开显示的维护者名称、联系邮箱和 GitHub 账号或组织。
- 创建或公开 GitHub 仓库。
- 配置 GitHub / GHCR 的外部账号权限和 Secrets。
- 正式发布 `1.0.6-beta.1`，或向社区、论坛和社交平台发帖。
- 产生付费服务、域名、托管或推广费用。

## 验收标准

- 公开仓库和完整历史通过敏感信息与许可证审计。
- 全新用户仅按公开文档可完成部署、初始化、Agent 接入、备份和卸载。
- GHCR 镜像、GitHub Release 和运行时版本完全一致且可校验。
- README、文档站、截图和视频全部来自虚拟演示数据。
- 外部贡献者可按文档建立开发环境并完成全部必需检查。
- Issue、Discussion、PR 和安全报告路径均可用且职责清楚。
- 未获得用户最终公开授权前，不创建公开仓库、不推送外部平台、不发布镜像和宣传内容。
