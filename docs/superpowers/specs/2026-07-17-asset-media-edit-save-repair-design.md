# 资产图片编辑与保存链路修复设计

## 背景

资产图片编辑目前存在“裁剪框不可见、缩放看似无效、保存结果不对应、多个编辑版本互相覆盖”的问题。问题同时跨越前端裁剪画布、媒体格式识别、对象存储路径、媒体版本模型和详情页展示关系，不能只在界面上补一个边框或刷新动作。

本设计归属 `asset-center` 模块，不新增独立模块。

## 已确认根因

1. 图片编辑弹窗通过依赖 `open` 的副作用读取画布节点。Radix Dialog 使用 Portal 延迟挂载内容时，副作用可能先于画布节点出现，导致 `stageSize` 一直为空，裁剪框、遮罩和实时裁剪内容不渲染；缩放值虽然变化，用户看不到实际效果。
2. 候选图导入时把媒体类型固定写成 `image/jpeg`。现有 UM690 原图实际是 `1080×1080 WebP`，版本记录却声明为 JPEG，导致 Blob 图片解码不稳定。
3. 新编辑版本在记录保存前使用空的 `version.Id` 生成对象路径，多个版本都写入 `renders/<asset>/<media>/.jpg`，后一次保存会覆盖前一次文件。
4. 图片库缩略图和大预览强制读取原始版本，而保存接口只更新同一媒体的 `active_version`。因此保存后的编辑结果在图片库中不可见，已存在的封面或图库关系仍可能引用旧版本。
5. 已有错误版本共享同一个对象路径，即使数据库中的裁剪参数不同，读取到的也可能是最后一次覆盖后的同一张图片。

## 选定交互方案

采用“每次保存生成新的独立图库图片”方案。

- 原图作为独立图片保留，例如 `UM690-01`。
- 从 `UM690-01` 裁剪保存后生成新的独立图片，例如 `UM690-02`。
- 再次编辑并保存继续生成 `UM690-03`，不覆盖任何已有图片。
- 新图片保存后立即出现在图片库并自动选中，预览显示最终 `16:9` 输出。
- 新图片不会自动设为封面或加入详情图库，仍由用户主动决定展示关系。
- 删除某张编辑结果只删除该独立图片，不影响它的来源原图和其他编辑结果。
- 每张独立图片都可以继续编辑；再次编辑仍生成新的图片，不做覆盖保存。

这套交互让用户只理解“原图、编辑后的新图、封面、图库”四个概念，不需要理解隐藏的版本树。

## 前端设计

### 裁剪画布

- 使用稳定的画布节点回调引用，而不是只在 `open` 变化时读取 `stageRef.current`。
- 画布节点出现后立即读取尺寸并注册 `ResizeObserver`；节点替换或弹窗关闭时释放观察器。
- 裁剪区域固定为 `16:9`，只允许缩放和平移。
- 原图始终按自身比例完整显示，裁剪框坐标以实际图片内容区域为基准，不包含画布留白。
- 裁剪框必须始终显示清晰边线、框外遮罩和中央拖动提示；框内实时显示保存后会保留的内容。
- 滑块和鼠标滚轮使用同一个缩放更新函数，缩放范围保持 `1×` 至 `4×`。

### 保存后的图片库状态

- 保存接口返回新建的媒体 ID 和版本 ID。
- 图片库刷新后自动选中新图片，缩略图和大预览直接显示新生成的 `1600×900` 图片。
- 原图卡片保持不变，新图片使用下一个设备图片编号。
- 封面和图库按钮继续操作当前选中的独立图片。

## Hub 与对象存储设计

### 真实媒体类型

- 上传和候选图导入都根据真实文件字节检测 MIME 类型，不信任来源 URL、响应头或固定扩展名。
- 对已有错误记录，读取对象时再次根据真实字节确定响应 `Content-Type`，无需先做破坏性数据库迁移即可恢复浏览器解码。

### 独立编辑结果

- 收到裁剪请求后，从选中图片的原始对象读取源图并按归一化裁剪参数生成 `1600×900 JPEG`。
- 预先生成新的 media ID 和 version ID，再构造唯一对象路径。
- 新建独立 `asset_media` 记录，`source_kind` 标记为编辑结果，名称使用下一图片编号。
- 新建该媒体自己的原始版本记录；对用户而言，裁剪结果就是这张新图片的原图，后续可再次编辑。
- 裁剪来源、来源版本、裁剪参数和比例写入版本 recipe，保留追溯信息。
- 对象写入或数据库保存失败时清理本次未完成对象，不能留下半成品记录。
- 不自动创建封面或图库 placement。

### 旧错误版本兼容

- 识别路径以 `/.jpg` 结尾或多个版本共享同一对象路径的旧 render 记录。
- 根据每个旧版本保存的 parent version 和 recipe，从原图重新渲染。
- 为每个旧版本生成包含真实 version ID 的独立对象路径，并更新对象键、字节数和 MIME 类型。
- 修复过程必须幂等：已经拥有唯一对象路径的记录不会重复生成。
- 现有 placement 继续指向原版本 ID，因此修复对象路径后详情页会恢复各自正确的裁剪结果。

## 数据流

1. 用户在图片库选择一张图片并点击“编辑图片”。
2. 前端读取该独立图片的原始对象，计算实际图片内容边界并显示 `16:9` 裁剪框。
3. 用户缩放或平移，前端只更新归一化 crop 参数和实时预览。
4. 用户点击“保存到图片库”，前端提交来源版本、crop 和 `16:9`。
5. Hub 渲染 `1600×900 JPEG`，创建新的媒体、版本和唯一对象文件。
6. 前端刷新媒体列表并选中新图片。
7. 用户根据需要设置封面或加入图库，详情页通过媒体变更事件立即更新。

## 错误处理

- 源对象不存在或无法解码时，保存失败并保留编辑弹窗和当前裁剪状态。
- 裁剪参数超出范围时由 Hub 规范化；宽高无效时拒绝保存。
- MIME 检测失败时拒绝导入并显示明确错误，不再伪装成 JPEG。
- 新对象写入失败时不创建媒体记录。
- 数据库保存失败时清理本次新对象并提示重试。
- 旧版本自动修复失败时保留旧记录并记录错误，不阻塞其他正常图片读取。

## 测试与验收

### 自动化测试

- WebP 原图能够以真实 MIME 类型读取。
- 两次编辑保存生成不同 media ID、version ID、对象路径和图片编号。
- 保存编辑结果不会修改来源原图文件。
- 新图片不会自动继承来源图片的封面或图库 placement。
- 不同裁剪参数生成的输出像素区域与 recipe 对应。
- 旧共享 `/.jpg` 对象路径可按各自 recipe 重建为独立文件，重复运行不产生新变化。
- 前端裁剪几何计算在正方形、横图和竖图下都保持 `16:9`。

### 浏览器验收

- 首次打开编辑弹窗即可看到裁剪框和框外遮罩。
- 滑块和鼠标滚轮都能实时放大、缩小图片。
- 拖动后裁剪框内看到的区域与保存后新图片一致。
- 保存后图片库新增下一个编号并自动选中。
- 原图仍然存在且内容不变。
- 未设置封面前详情页不变化；设置新图片为封面后详情页立即显示新图，无需刷新页面。
- 控制台无相关 error 或 warn。

## 非目标

- 本轮不增加自由比例、旋转、滤镜、AI 去水印或批量编辑。
- 本轮不改变固定 `16:9` 和 `1600×900` 的统一展示标准。
- 本轮不自动决定哪张图片应该成为封面。
