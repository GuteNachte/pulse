# Pulse 上线前功能拆解与实现逻辑

> 目标：把 Pulse 1.0.5 打磨到能上线的程度。本文不按代码文件讲，而是按用户能理解的功能模块拆解：这个功能做什么、背后怎么跑、关键判断逻辑是什么、上线前要验什么。

## 阅读规则

- `已验证`：本轮已从项目文档或代码入口确认。
- `来自现有文档`：来自 `docs/` 里的项目说明，后续如果部署环境变化需要再确认。
- `我的判断`：基于当前代码结构和产品目标给出的上线建议。
- 每个模块后续都要补齐：功能边界、实现链路、真实数据来源、失败处理、权限规则、上线验收点。

## 总体架构

已验证：Pulse 当前由四部分组成：

- Web 前端：React / Vite 页面，负责展示、配置、确认操作和移动端界面。
- Hub 后端：PocketBase + 自定义 Go API，负责用户、机器、采集数据、操作下发、告警、发布版本和备份。
- Agent：Windows 主机版与 Linux / NAS 容器版，负责采集机器数据、执行受控操作并通过 WebSocket 连接 Hub。
- Android App / PWA：复用 Web 前端移动端布局，Android 作为 Capacitor 壳，移动端不是 Agent。

核心数据流：

1. Agent 启动后拿 `TOKEN` / 配对凭据连接 Hub。
2. Hub 校验身份，把 Agent 绑定到某台机器记录。
3. Agent 定期上报系统指标、容器、硬件详情、软件服务等真实采集数据。
4. Web 从 PocketBase collections 和 `/api/pulse/*` API 读取数据。
5. 用户发起危险操作时，Web 必须确认，Hub 校验权限、机器状态、Agent 能力和保护规则，再下发给 Agent。
6. 操作结果写入 `operation_actions` 和 `operation_audit`，页面展示进度和历史。

## 功能总目录

### 1. 登录、用户和权限

用户看到：

- 首次运行创建账号。
- 登录后进入首页。
- 管理员可以管理用户、备份、日志等。
- 只读用户不能执行写入和危险操作。

实现逻辑：

- Hub 基于 PocketBase `users` 认证。
- `/api/pulse/create-user` 只在没有用户时开放。
- 大多数 `/api/pulse/*` 接口要求登录。
- 写操作额外排除 `readonly` 角色。
- 用户管理和备份接口要求 `admin` 角色。

上线关注：

- 首次初始化不能被重复打开。
- 只读用户必须无法添加机器、删除机器、执行容器 / 服务 / Agent 更新操作。
- 正式环境不能保留开发默认账号。

### 2. 机器添加与 Agent 接入

用户看到：

- 客户端页点击“添加系统”。
- 选择 Windows 或 Linux 容器。
- 填目标 IP、机器类型、主要用途、NAS、说明、是否加入离线告警。
- 点击添加后生成安装会话。
- 复制安装命令到目标机器执行。
- 点击检测安装，只有 Agent 真正配对并上线后才添加成功。

实现逻辑：

- 添加机器不再预创建正式机器记录。
- Web 调用 `/api/pulse/pairing-codes` 创建一次性配对码。
- Hub 保存配对码、目标 IP、创建用户和过期时间。
- Agent 安装命令执行后调用 `/api/pulse/agent-pair`。
- Hub 校验配对码、过期时间、是否已使用、请求来源 IP 是否匹配目标 IP。
- 校验通过后 Hub 创建 `systems` 机器记录和 `fingerprints` 凭据。
- Agent 再通过 WebSocket 连接 `/api/pulse/agent-connect`。
- 检测安装时，Web 查询配对码状态，再确认对应机器状态是否 `up`。

关键逻辑：

- 目标 IP 是防止配对码被错误机器使用的安全边界。
- 机器名称来自 Agent 上报的真实主机名，不靠用户手填。
- NAS 是独立字段，只由用户勾选决定，不再通过机器名或用途推断。
- “加入告警”默认不勾选；不勾选时保存为 `suppress_offline_alerts=true`，机器离线不触发离线告警。
- 配对成功后才写入机器类型、主要用途、NAS、说明和离线告警配置。

上线关注：

- 配对码过期、目标 IP 不匹配、Agent 安装失败、Agent 配对成功但 WebSocket 未上线都要有明确提示。
- Windows 安装命令和 Linux Docker Compose / `docker run` 必须都能跑通。
- 本地开发复制命令不能使用 `localhost` 给远程 Agent。
- 正式部署 Hub 同机 Agent 不走手动添加，而是由标准 Compose 自动注册 Hub 机器。

### 3. Hub 同机 Agent 与机器身份

用户看到：

- 安装 Hub 的机器自动出现在客户端列表。
- 名称显示真实机器名。
- 只用 `Hub` 标签标识，不显示“本机”或括号后缀。
- Hub 机器不能删除。

实现逻辑：

- 标准部署里 Hub 和 Agent 同机运行。
- 同机 Agent 使用 loopback-only 本机 Token。
- Hub 只在来源为 loopback 且符合本机 Token 规则时标记 `is_local`。
- 删除机器时，后端根据 `is_local` 阻止删除。
- 开发环境通过脚本显式开启开发开关，避免把远程机器误标为 Hub。

上线关注：

- 非 Hub 机器不能误显示 Hub 标签。
- Hub 同机 Agent 的 IP、机器名、用途不能被历史数据污染。
- 删除保护必须在后端生效，不能只隐藏 UI。

### 4. 首页与客户端列表

用户看到：

- 首页展示总体状态、最近机器、网站状态、告警摘要。
- 客户端页展示所有机器、状态、IP、标签、CPU / 内存 / 磁盘 / GPU / 网络等摘要。

实现逻辑：

- Web 从 `systems`、`system_stats`、`alerts` 等数据派生摘要。
- 指标展示统一走真实性规则：离线、暂停、待接入、未采集不能显示伪造 0%。
- IP 来自 Hub 记录的 Agent WebSocket 真实来源 `info.ip`。

上线关注：

- 离线机器不要显示实时指标。
- 缺失数据要显示“未采集”，不能显示正常。
- 标签必须来自真实字段，不靠名称推断。

### 5. 机器详情页

用户看到：

- 顶部显示机器名、标签、说明、真实 IP、系统、CPU、内存、网卡、GPU。
- 摘要卡显示 CPU、内存、磁盘、网络、GPU、容器。
- 点击摘要卡进入对应模块详情。
- 软件与服务、网站监控、操作记录、编辑机器在详情页可用。

实现逻辑：

- 页面由 `systems`、`system_stats`、`system_details`、`containers`、`smart_devices` 等数据组合。
- 摘要卡逻辑集中派生，避免每个页面重复判断。
- 设备能力条只展示主要真实采集能力：基础指标、容器、S.M.A.R.T.、GPU。
- 未发现模块点击提示，不跳黑屏。

上线关注：

- 所有标签和指标必须来自真实采集或真实配置，不能用占位。
- 机器详情不能因为某个模块无数据而白屏。
- 虚拟机、NAS、Hub、物理机等标签口径必须统一。

### 6. 基础指标与硬件详情

用户看到：

- CPU：使用率、频率、厂商标签、核心明细。
- 内存：使用率、总量、DDR / LPDDR 代际。
- 磁盘：容量、SSD / HDD 标签、SMART 详情。
- 网络：实时速率、链路速率、DHCP / 静态 IP、网关、DNS、IPv4、IPv6。
- GPU：核显 / 独显标签、负载、显存、功耗。

实现逻辑：

- Agent 负责采集原始硬件和指标。
- Hub 保存最新详情和时间序列指标。
- Web 只展示真实采集字段；识别不到时不显示标签。
- SMART 设备每轮保存后会删除同机器已消失的旧设备，避免残留误导。

上线关注：

- 虚拟机不能因为 Agent 能力声明就显示 S.M.A.R.T. 可用，必须有真实设备。
- 磁盘数量、类型、内存代际、网卡速率都必须和真实机器一致。
- 老数据残留要能清理。

### 7. 容器监控与控制

用户看到：

- 容器页按机器查看 Compose 编排和独立容器。
- 可启动、停止、重启、更新镜像。
- Compose 编排可批量操作。
- Pulse 自身容器不能通过通用容器页操作。

实现逻辑：

- Agent 通过 Docker / Podman socket 采集容器。
- Hub 根据 Compose labels 归类编排。
- 操作统一走 `/api/pulse/operations`。
- Hub 校验操作动作、目标容器、机器在线、Agent 能力和保护规则。
- Pulse 相关容器保护在后端实现，包含 Pulse 容器的编排也会阻止批量操作。
- 操作结果写入操作记录和审计记录。

上线关注：

- Docker socket 权限不足时要明确提示。
- Pulse 自身保护不能被前端绕过。
- Compose 编排识别不能把 `pulse-agent` 错归到业务编排。
- 更新镜像要有进度和失败信息。

### 8. 软件与 Windows 服务监控

用户看到：

- 只在 Windows 机器详情页显示软件与服务入口。
- 可以搜索软件和 Windows 服务。
- 软件只监控运行状态。
- 白名单内 Windows 服务可启动、停止、重启。

实现逻辑：

- Hub 搜索接口转发到对应 Agent。
- 监控规则保存到规则表。
- Agent 按规则采集状态并写入 `monitored_software` / `monitored_services`。
- 服务控制走统一操作接口。
- 受保护 Windows 服务在 Hub 后端阻止操作。

上线关注：

- Docker / containerd / Podman 等容器运行时不能作为普通软件误加入。
- 保护服务不能被控制。
- 删除规则后状态表要清理，不能留下脏状态。

### 9. 网站监控

用户看到：

- 网站监控页可添加服务。
- 一个服务可以配置多个地址。
- 地址可标注内网 / 外网、IPv4 / IPv6。
- 能看到状态、响应时间、检测历史。
- 系统详情页能展示归属该机器的网站监控。

实现逻辑：

- 网站配置和地址保存在 Hub。
- Hub 按地址类型发起检测。
- 检测记录按地址保存历史。
- 页面从检测历史派生最新状态、待检测、异常和响应趋势。

上线关注：

- IPv6 检测取决于 Hub 运行网络命名空间。
- 未检测不能显示正常。
- 机器归属和筛选不能丢。

### 10. 告警与通知

用户看到：

- 告警中心查看触发和恢复记录。
- 告警设置统一配置资源类告警。
- 网站、容器、软件、服务异常会进入告警体系。
- 通知设置里配置站内告警、Android 通知说明和外部通道。

实现逻辑：

- Hub 维护当前告警和历史告警。
- Web 订阅告警 realtime。
- Android App 打开或后台 WebView 存活时，把新告警转为系统通知。
- 外部通知通道失败会记录失败原因。

上线关注：

- 新机器默认不加入离线告警，必须用户明确勾选。
- 告警恢复要自动标记恢复。
- App 被系统杀掉不承诺远程推送，这个限制必须保留说明。

### 11. 操作记录与审计

用户看到：

- 危险操作需要确认。
- 执行后显示运行中、成功、失败。
- 可查看操作记录和审计记录。

实现逻辑：

- 前端提交操作时必须带 `confirm=true`。
- Hub 只允许白名单动作。
- 参数会校验并脱敏。
- 操作状态写入 `operation_actions`。
- 每次成功或失败都写入 `operation_audit`，包含用户、机器、动作、目标、结果、来源 IP。

上线关注：

- 所有危险操作都必须走统一确认。
- 失败不能静默。
- Token、secret、password 等敏感参数不能明文写入记录。

### 12. Agent 管理与版本更新

用户看到：

- 设置页 Agent 管理分 Windows 主机版和 Linux / NAS 容器版。
- 展示当前 Agent 版本、目标版本、是否可更新、阻塞原因。
- 点击更新后执行受控更新。

实现逻辑：

- 发布流程生成 Agent release 记录。
- Hub 同步本地 manifest 到 `agent_releases`。
- Windows Agent 更新下载二进制并替换服务。
- Linux 容器版 Agent 使用 Docker / Podman socket 拉镜像并重建自身容器。
- Agent 比较版本号；已是目标版本时只返回已最新。

上线关注：

- 版本仓库不能显示不存在的镜像或包。
- Hub、Web、Agent、Android App 版本必须同号。
- 发布脚本不能允许跳过某一端正式发布。

### 13. 设置页、备份、日志、用户、高级入口

用户看到：

- 常规设置：主题、图表时间、单位、阈值。
- 通知设置：站内告警、Android 通知说明、外部通道。
- Token：Agent 接入 Token 管理。
- 日志：系统日志列表和详情。
- 备份：创建、下载、还原、删除。
- 用户：添加、编辑、重置密码、删除。
- 高级：PocketBase 后台入口。
- 关于：版本、Hub 地址、更新记录。

实现逻辑：

- 常规设置存用户偏好。
- 管理类能力由 Hub 自定义 API 提供。
- 高风险操作有确认。
- 关于页版本记录从独立 release history 数据渲染。

上线关注：

- 管理员权限边界要清楚。
- 备份还原是高风险操作，需要强确认。
- 关于页必须完整记录每个版本、每个端改动。

### 14. 移动端 / Android App

用户看到：

- 手机端使用底部导航：首页、机器、告警、网站、容器。
- 设置等入口在更多 / 设置入口里。
- 手机端列表优先，详情用 Sheet 或独立详情。
- Android 首次配置 Hub 地址。

实现逻辑：

- 复用 Web 前端和 API。
- `useMobileLayout()` 控制移动 / 桌面分流。
- Android App 通过 Capacitor 壳保存 Hub 地址和接入系统通知。
- 离线只读快照只展示缓存，不允许执行操作。

上线关注：

- 手机、平板、桌面三套宽度不能互相破坏。
- 离线状态所有操作必须禁用。
- Android App 版本必须跟 Hub / Web / Agent 同步。

### 15. 发布、部署和版本规则

用户看到：

- 关于页显示统一版本。
- 发布说明按 Web / Hub、Android、Agent、部署 / 发布、版本规则分类。

实现逻辑：

- 发布入口是 `supplemental/scripts/publish-release-v1.ps1`。
- 版本一致性检查覆盖 Web、Hub、Agent、Android、Dockerfile、Compose、安装文档和发布脚本。
- Harbor 镜像使用显式 tag，不使用 `latest`。
- FlyNAS 正式部署目录是 `/vol1/1000/docker/pulse`。

上线关注：

- 不能只发布 Web 或只发布 Hub。
- 同名 tag 更新后，正式机器必须 `docker compose pull && docker compose up -d --force-recreate`。
- 本机 Docker Desktop host 网络不能代表正式 NAS 环境。

## 上线前总验收路线

我的判断：上线前不应该只跑构建，必须按真实用户路径验。

1. 账号与权限：首次用户、管理员、只读用户。
2. 添加机器：Windows、Linux / NAS、目标 IP、配对码、检测安装、失败提示。
3. Agent 上线：WebSocket、真实 IP、真实机器名、Hub 标签、不能删除 Hub 机器。
4. 基础监控：CPU、内存、磁盘、网络、GPU、SMART、容器，缺失数据不能显示假正常。
5. 容器操作：单容器、Compose、更新镜像、Pulse 自身保护。
6. 软件与服务：搜索、添加规则、状态采集、服务控制、保护服务拒绝。
7. 网站监控：内网 / 外网、IPv4 / IPv6、待检测、异常、恢复。
8. 告警通知：资源告警、离线告警 opt-in、网站 / 容器 / 服务告警、通知失败记录。
9. 设置管理：常规、Token、Agent 管理、通知、日志、备份、用户、关于。
10. 移动端：手机、平板、Android App、离线只读快照、危险操作确认。
11. 发布链路：版本一致性、Hub / Agent / Android 同版本构建、Harbor 镜像、FlyNAS 重建和运行态版本确认。

## 下一步拆解顺序

建议按上线风险从高到低继续：

1. 机器添加与 Agent 接入闭环。
2. Agent 真实采集和系统详情显示真实性。
3. 容器监控与操作保护。
4. 告警和通知。
5. 网站监控。
6. Windows 软件与服务。
7. 设置、用户、备份、日志。
8. 移动端 / Android。
9. 发布部署和版本一致性。
