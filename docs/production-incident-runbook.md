# Pulse 正式环境故障处置清单

> 适用于家庭正式环境的 Hub、容器版 Agent、Windows Agent、反向代理和数据异常。目标是先保护数据和证据，再恢复服务，最后修复根因。

## 0. 先记住三条底线

- 不确定影响范围时，不删除数据、不执行 `down -v`、不覆盖 `pulse_data`、不降级数据库。
- 生产环境的重启、回滚、恢复、权限调整、代理调整和数据清理，先说明影响并取得确认。
- “服务恢复”不等于“故障解决”；根因、验证结果和后续风险必须留下记录。

## 1. 第一轮判断

记录开始时间（使用服务器本地时间）、发现人、现象、影响范围和当前版本。

按现象分组：

- 网页打不开：先区分反向代理、Hub 进程 / 容器、网络和浏览器问题。
- Hub 健康检查失败：优先检查 Hub 日志、容器状态、磁盘空间和 `pulse_data` 是否仍挂载。
- Agent 失联：区分 Agent 进程停止、WebSocket 认证失败、网络不可达和采集超时。
- 数据异常或消失：立即停止清理、迁移和恢复操作，保留当前数据目录与日志。
- 升级失败：保留新版本产物和日志，不直接删除新目录；按发布回滚手册准备上一版本和升级前备份。
- 凭据或权限疑似泄露：先限制外部访问并准备轮换 Token / 密码，不在聊天、截图和日志中复制秘密内容。

## 2. 先保存证据

至少保存：

- 当前 Hub / Agent / Compose 版本和镜像 tag。
- `docker compose ps`、容器日志最后 100 行、Hub `/api/health` 结果。
- 受影响机器的页面状态、Agent 最近连接时间和错误摘要。
- 故障前后执行过的命令、时间和操作者。
- 当前备份列表、最近一次备份校验结果和可用恢复点。

不要保存：Token、密码、邮箱授权码、私钥、完整连接码和带秘密字段的配置原文。

## 3. 按故障类型恢复

### 网页或 Hub 不可用

1. 从本机或局域网访问 `/api/health`，确认是否只有反向代理异常。
2. 检查 Hub 进程 / 容器是否运行、端口是否被占用、磁盘是否已满。
3. 检查 `pulse_data` 挂载和最近日志，不要先删除容器或数据目录。
4. 只有确认当前版本进程异常且证据已保存后，才申请重启 Hub。
5. 重启后验证健康接口、登录、资产、系统列表、实时状态和日志。

### Agent 失联

1. 在网页查看最近在线时间、实际 Agent 版本和连接错误。
2. 检查 Agent 服务 / 容器状态和日志，区分认证失败、网络失败和采集超时。
3. 认证失败时不要反复重置配对码；先确认 Hub、机器和凭据对应关系。
4. 采集超时时保留基础状态，不把一次慢采集直接当成机器离线。
5. 恢复后确认原系统 ID 重新上线，没有产生重复机器。

### 升级失败或启动异常

1. 停止继续重试，保存新版本日志和容器状态。
2. 确认升级前完整备份、上一已验证版本和 Compose 项目名。
3. 按 `docs/release-deployment-runbook.md` 同时恢复上一版本镜像和升级前数据。
4. 禁止把新版本写过的 `pulse_data` 直接交给旧 Hub。
5. 回滚后验证健康接口、登录、核心数据数量、Agent WebSocket 和版本一致性。

### 数据异常或误删

1. 立即停止可能继续写入或清理数据的任务。
2. 不覆盖当前数据目录；先保留现场并确认最近可用备份。
3. 先在隔离临时目录做恢复预检，确认数据库、资产、接口、关系、设置和文件可读取。
4. 恢复正式数据前再次确认影响范围、备份和回退方法。
5. 恢复后核对核心集合数量、账号权限、图片附件、监控时间线和 Agent 接入。

## 4. 何时必须暂停并请求确认

- 需要停止正式服务、回滚版本、恢复备份、清理数据或修改权限。
- 需要改变公网访问、反向代理、证书、认证或 Agent 暴露范围。
- 发现疑似凭据泄露、未授权访问或高权限 Agent 异常行为。
- 无法确认备份可恢复，或当前操作可能覆盖唯一数据副本。

## 5. 故障结束标准

同时满足以下条件才能标记“已恢复”：

- 服务健康接口正常，页面可登录。
- 受影响 Agent 使用预期版本并恢复连接。
- 资产、接口、关系、账号和主要设置核对无误。
- 监控、告警、实时刷新和关键操作实际验证通过。
- 日志中没有持续新增的同类错误。
- 已记录根因、修复动作、验证证据、残余风险和是否需要继续观察。

高风险故障恢复后至少观察 3 天；普通功能故障至少观察 24 小时。观察期间发现同类异常，恢复计时重新开始。
