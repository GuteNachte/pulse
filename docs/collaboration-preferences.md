# Pulse 项目专属协作约定

> 这里仅保存 Pulse 项目专属规则。通用协作方式请查看 Codex 用户目录中的全局规则文件。

## 项目专属规则

- Pulse 现阶段主要服务用户本人和家庭使用；功能取舍优先简单、稳定、容易理解和长期维护，不为尚未确定的公开商业化场景过早增加复杂度。
- Pulse 现阶段的功能优先级为：第一，家庭设备管理；第二，监控与告警；第三，自动化管理。先把设备资产、关系和状态整理清楚，再完善异常发现与通知，最后在边界和安全措施明确后增加远程操作及自动联动。
- Pulse 的功能只有达到完整可用才算完成：主要流程可正常使用，与改动匹配的测试通过，用户可见页面经过实际检查，失败和异常有容易理解的中文提示，相关文档、版本记录及设置页关于记录同步更新；未满足这些条件时要明确标记为开发中或待完善。
- Git 本地提交按完整小阶段组织：一个可以独立说明的功能或一轮基础建设完成并验证后，先向用户说明改动范围，再创建一次本地提交；不要把大量无关改动混在一起，也不要为每个细小编辑制造零碎提交。推送 GitHub、创建 Pull Request、发布版本或部署正式环境仍须单独确认。
- 日常低风险开发操作由 Codex 自动完成，包括读取和检索项目内容、修改项目文件、运行项目已有测试、类型检查、本地构建及查看本地日志。安装插件、技能、MCP、开发工具、SDK 或依赖，以及删除或覆盖数据、修改外部系统、推送 GitHub、发布版本、部署、迁移、回滚或重启正式服务等操作，必须提前用中文说明影响并取得用户确认。
- Pulse 默认使用中文沟通、中文文档和中文 UI 文案；命令、路径、代码标识、镜像名和 URL 保持原样。
- 开发前必须读取项目规则、启动清单、运行手册、版本说明和相关模块文档。
- 本地源码预览固定使用 Hub 8090 和 Vite 5173；Docker 只用于发布前等价测试和最终镜像打包。
- 从 1.0.6 起按基础底座加可管理功能模块演进；新增功能必须先确认模块归属、独立目录、manifest、开关语义和设置页可观测性。
- 资产中心是资产、接口、关系和位置主数据源；监控、拓扑、告警、通知和智能家居优先消费已确认的资产信息。
- 行为链路问题必须按复现、定位根因、修源头、端到端验证、写入版本说明处理。
- 每次用户可见或发布相关改动都要追加 docs/release-notes-next.md，并同步维护设置页关于的版本记录。
- 发布时 Hub、Agent、Web 和 Android App 使用同一个显式版本号；Android 当前暂停开发，未重新确认前不安装或构建 Android 环境。
- 发布和部署不使用 latest；正式部署与容器版 Agent 默认使用 network_mode: host。
- Harbor、FlyNAS、Agent 安装、备份、回滚和数据迁移遵循对应的项目文档，不把敏感信息写入仓库。
- Pulse 的数据库迁移、批量数据修改、恢复、升级和正式部署必须遵循项目备份文档；先确认备份存在且可恢复，再执行可能影响数据的操作。
- Pulse 已具备域名、公网 IP 和反向代理基础；需要从家庭网络外访问时，优先复用现有反向代理和 HTTPS，不重复搭建远程访问体系，也不直接暴露不必要的 Hub、数据库、管理或 Agent 端口。正式接入或调整前必须核对域名、证书、认证、访问范围、日志和回退方法，并取得用户确认。
- Pulse 的家庭成员每人使用独立账号：用户本人使用管理员账号，家庭成员使用各自的普通账号，不共享管理员密码。普通账号默认只开放查看和日常使用所需权限，高风险设置和管理操作仅对管理员开放；创建真实账号或调整正式权限前必须取得用户确认。
- 普通家庭账号默认可以查看设备、状态、拓扑、监控和告警，也可以确认或处理日常告警、编辑设备备注及维护少量非关键设备信息；删除数据、远程控制、账号与权限管理、系统设置、部署和其他高风险操作仅允许管理员执行。具体权限实现时遵循最小必要原则，并经过实际账号验收。
- Pulse 告警按重要程度分级通知：普通异常和短暂波动只在 Pulse 内记录；设备持续离线、硬盘健康风险、连续监控失败等重要异常才通过已确认的外部渠道主动通知。重复告警应合并并设置合理的等待时间，同时提供恢复通知；外部通知失败时，Pulse 内仍须保留告警及失败原因。接入任何外部通知服务前必须先取得用户确认。
- Pulse 第一版外部告警渠道采用邮箱：普通异常只保留站内通知，重要异常发送告警邮件，状态恢复后发送恢复邮件。邮箱接入优先使用主流标准方式，发信账号、授权信息和收件人不得写入仓库；配置真实邮箱、保存凭据或发送测试邮件前必须向用户说明所需信息和影响，并取得确认。
- Pulse 监控目标存在期间只保留最近 30 天的详细监控数据和告警历史，超过 30 天自动清理，不再长期保留更早的监控指标、告警和恢复记录；删除监控目标时按项目规则彻底删除该目标的全部历史监控数据、告警和恢复记录。关键操作审计不属于监控历史，按操作审计规则继续保留。自动清理每天凌晨 03:00 按服务器本地时间统一执行，不因打开网页或查看页面临时触发；当前不提供网页手动清理按钮，成功时不在网页弹出提示，任务执行前后记录清理范围、数量和结果，失败时仅写入日志并保留未清理数据，首次实施前必须明确清理范围、预计空间变化、备份与恢复方法，并经过测试验证和用户确认。
- 高级设置提供管理员专用的“清理全部监控数据”入口。确认后删除所有机器的监控指标、采集明细、告警历史、恢复记录以及温度、GPU、磁盘、容器、服务、软件等监控历史；清理完成后只保留本次清理操作的审计记录，不保留任何监控历史副本。资产资料、用户账号、权限、网页设置和机器连接配置继续保留，所有监控从当前时间重新开始记录。操作不可恢复，采用中文两步确认：第一次点击后显示完整风险说明，第二次点击“确认清理全部监控数据”即可执行，不要求输入文字；执行时显示“正在清理”状态，完成后按指标、告警、恢复记录、采集明细等类别分别显示删除数量，并明确资产资料和机器连接配置未受影响；实施前必须再次说明影响并取得用户确认；失败只显示“监控数据清理失败”，详细原因写入日志。
- Pulse 采用每日自动备份，并按近期、每周和每月分层保留：日常变化每天留档，每周和每月保留较长期的恢复点。具体保留数量、备份位置和空间上限在实施前另行确认；自动备份必须检查执行结果，失败时在 Pulse 内留痕并按重要告警处理。创建定时任务、写入正式存储或首次执行真实备份前必须取得用户确认。
- Pulse 备份暂时保存到一个独立的本地备份文件夹，不接入云存储或第二台设备。备份目录必须与程序工作目录和正式运行数据目录分开，不能放进 Git 仓库；具体路径在实施前根据运行设备和可用空间引导用户确认。需要明确说明：本地单副本可以应对误删、升级失败等问题，但不能防止整块磁盘或整台设备同时损坏，后续如保护需求提高再单独确认增加异地副本。
- Pulse 自动备份默认保留 7 份每日备份、4 份每周备份和 12 份每月备份；清理时只删除超过保留数量且已确认完整的最旧备份，不影响当前数据，也不删除最后一个可用恢复点。首次启用自动清理前必须预估空间占用、验证备份完整性并取得用户确认。
- Pulse 每月执行一次备份恢复测试：使用临时目录或隔离环境恢复最新可用备份，检查数据库、设置、资产资料和主要文件能否正常读取，并记录测试时间和结果。恢复测试不得覆盖、连接或修改正式数据；创建自动测试任务、占用正式存储或首次执行真实恢复验证前，必须向用户说明操作方式、空间需求和清理方法并取得确认。
- Pulse 正式环境采用稳定后再更新的方式：新功能先在本地完成开发、针对性测试、页面实查和发布前完整检查，确认正式备份可用且回退步骤明确后，才允许更新家庭正式环境。安全漏洞或影响正常使用的紧急故障可以走加急流程，但仍不得跳过备份、必要验证、回退准备和用户确认；构建发布物、推送镜像、部署或重启正式服务均须单独确认。
- Pulse 界面设计优先简单易懂：默认使用清楚的中文文案，减少完成常用任务所需的步骤，让设备状态、重要告警和下一步操作一眼可见；高级和低频功能放在合适的二级入口，不为视觉效果增加无必要的动画、装饰或操作负担。界面改动必须同时检查桌面与移动宽度下的可读性、操作反馈和异常状态。
- Pulse 新增的可选功能模块默认关闭，由用户在设置页查看模块用途、状态、依赖和影响后主动开启；认证、权限、数据管理、模块管理等基础底座能力不属于可关闭模块。模块关闭后应停止对应入口、后台任务和不必要的资源占用，同时保留用户数据并清楚说明重新开启后的行为；修改现有模块默认状态或正式环境开关前必须取得用户确认。
- Pulse 的功能想法、问题和优化建议统一记录在 `docs/project-backlog.md`，并标明类型、优先级、当前状态、验收目标和必要背景；准备开发时再整理成范围清楚的具体任务。聊天中的重要决定应及时落入待办或正式项目文档，避免只留在对话中；同步到 GitHub Issues 或其他外部平台前必须取得用户确认。
- Pulse 项目待办采用四级优先级：紧急、重要、普通、以后再做。紧急用于正式环境不可用、数据安全风险、严重权限或安全问题；重要用于明显影响主要使用流程或近期目标的问题；普通用于不阻塞使用的一般功能和优化；以后再做用于方向已认可但当前没有必要投入的想法。优先级由 Codex 根据影响范围、风险和项目目标提出建议，用户可随时调整。
- Pulse 默认不向外部服务发送设备信息、使用统计、错误日志、诊断数据或其他遥测内容。需要排查问题时，先在本地分析；确需导出或发送日志时，必须提前说明内容、用途、接收方和潜在敏感信息，经用户确认并完成脱敏后，只提供解决问题所需的最少内容。邮箱告警等由用户主动配置的必要通信不属于使用统计，但仍须遵守凭据保护和最少数据原则。
- Pulse 的密码、Token、邮箱授权码、私钥和其他秘密信息必须保存在项目目录外的专用受保护配置或秘密文件中；仓库只保留示例名称和无真实值的配置模板。创建或迁移真实秘密配置前，必须确认保存位置、访问权限、备份和换机迁移方法，日志、文档和测试输出中不得泄露秘密值。
- Pulse 正式环境发生故障并影响家庭正常使用时，先使用已验证且可回退的方法恢复服务，同时保留日志、版本、配置和故障时间等现场证据；恢复后必须继续定位根因、修复源头并完成端到端验证和版本记录。若故障可能继续损坏数据或扩大安全风险，应先隔离风险；重启、回滚、恢复备份或覆盖配置前仍须取得用户确认。
- Pulse 的重要功能、跨模块改造、权限调整、数据结构变化和正式运行链路改造在开发前必须先确认简短中文设计，至少说明目标、主要页面或流程、真实数据来源、模块归属、权限与安全影响、风险和验收标准；用户确认产品方向后再实施。目标明确的小修复、文案调整和低风险小改动可以直接执行，并按改动范围完成验证和记录。
- Pulse 引入第三方依赖或开源组件时，优先选择主流成熟、维护活跃、安全记录清楚、许可证适合且符合现有技术栈的方案；能够可靠复用现有能力时不新增依赖。安装或升级前必须检查必要性、维护状态、安全风险、许可证、体积和替换难度，并向用户说明后取得确认。
- Pulse 每个完整开发阶段结束时，必须核对本阶段涉及的项目规则、待办状态、运行手册、测试说明、About 记录和版本说明是否与实际结果一致；只更新受影响内容。正式发布前再全面检查文档中的版本、路径、命令、环境和已完成功能，及时修正过期或矛盾信息。
- Pulse 的重要项目决定保留简短原因记录：写清决定内容、选择原因、确认时间或版本，以及未来什么情况需要重新评估；不把整段聊天复制进项目。项目定位、功能优先级、权限、备份、通知和发布策略等决定应在对应项目文档或待办中可追溯。
- Pulse 的需求描述不够清楚时，先读取现有实现、项目规则、历史决定和主流方案，再把需要用户决定的产品效果整理成最多三个中文选项，说明影响并标出推荐项；能够沿用项目现有模式安全确定的技术细节由 Codex 主动处理。涉及产品方向、权限与数据取舍、高风险操作或无法可靠推断的真实信息时，必须再向用户确认。
- Pulse 开发过程中发现计划外问题时，先判断是否阻碍当前功能、影响数据或安全、导致验证失真，或属于必须一起修复的关联问题；这类问题在说明影响后纳入当前阶段处理。无关且不紧急的问题只记录到项目待办，不擅自扩大本次范围；无法判断时先向用户说明影响和选择。
- Pulse 代码质量检查发现问题时，按风险分批修复：先处理功能错误、权限越界、数据风险、安全问题和构建失败，再处理格式与一般规范；每批改动后运行匹配的测试，避免一次性改动大量无关文件。暂不修复的问题要记录原因、风险和后续计划。
- Pulse 功能或数据结构升级优先使用自动兼容迁移：升级前先备份，迁移保留原始数据和回退路径；失败时停止并恢复，不让半成品数据继续运行；完成后验证资产、关系、设置、权限和主要流程，全部通过后才算升级完成。真实数据迁移、覆盖或删除前必须向用户说明影响并取得确认。
- Pulse 测试默认只做必要测试：覆盖主要功能流程、数据安全、服务稳定性和用户可见结果；补充性、重复性、低概率极端场景测试默认不做，只有发现实际风险、改动触及对应边界或用户明确要求时才增加。必要测试不足以证明安全或稳定时，必须先说明缺口和风险。
- Pulse 的关键流程必须有自动测试保护，至少覆盖登录与权限、资产及关系数据、Agent 接入、监控与告警、备份恢复和数据迁移等高风险链路；界面外观、桌面与手机布局及真实交互同时使用浏览器实查。测试深度按风险和改动范围确定，不为追求数量编写低价值测试。
- Pulse 的用户可见功能完成前必须从普通家庭用户角度进行实际体验检查：走通主要流程，确认中文提示、按钮位置、状态说明、操作反馈和错误后的下一步容易理解；电脑端与手机网页按各自重点检查。体验检查与权限、数据、接口和异常链路测试缺一不可，全部满足后才算完整可用。
- Pulse 涉及数据、权限、Agent 接入、监控告警、备份恢复和正式运行链路的重要功能，在正式部署后必须设置与风险相匹配的观察期，持续检查错误日志、性能、告警、数据状态和家庭实际使用情况；观察期内保留回退准备，确认稳定后才关闭待办。普通文案、样式和低风险小改动完成验证后无需设置观察期。
- Pulse 重要功能观察期按风险分级：一般重要功能默认观察 24 小时；涉及数据迁移、权限、备份恢复、Agent 稳定性或其他高风险正式链路的改动观察 3 至 7 天；出现异常、数据波动或关键告警时延长观察期并重新计算稳定时间。部署前必须明确本次观察时长、重点指标、异常处理和结束条件。
- Pulse 重点保证采集端 Agent 轻量、稳定并适合长期运行，严格关注其 CPU、内存、磁盘、网络和后台任务占用；在线状态与重要告警保持必要及时性，一般指标和低优先级采集按实际价值设置合理频率，不为图表更密集而高频采集。新增或调整 Agent 采集频率前必须评估被采集设备负载、网络影响和 Hub 数据增长。Web 网页端不设置苛刻的极限资源目标，以交互流畅、稳定、无明显卡顿和无明显资源浪费为验收标准，不为压低少量占用牺牲功能完整性和可维护性。
- Pulse 的设备、Agent 或网络暂时离线时，保留最后一次有效数据用于排查，但页面必须明确显示离线状态、最后在线时间和数据采集时间，并把旧数据标记为历史值，不能当作当前实时状态。连接恢复后自动继续采集；离线和恢复事件按分级告警规则记录，避免重复通知。
- Pulse 遇到设备不支持、Agent 能力未开启、运行权限不足、依赖缺失或采集失败时，页面必须如实显示“不可用”、具体原因和可行的下一步，不能显示为 0、正常或笼统的暂无数据。Hub、Agent 和 Web 应区分不支持、未启用、权限不足、暂时失败、未知状态和真实零值，优先修复真实能力状态与数据来源，不只在页面上遮盖。
- Pulse 的网络请求、状态查询、采集和通知等可安全重复操作遇到临时故障时，采用有限重试和逐步延长间隔；达到上限后停止，记录最后失败原因并按影响告警。删除、远程控制、批量修改、恢复备份和覆盖配置等高风险操作不得自动重复执行；确需重试时必须具备防止重复生效的保护，并再次取得用户确认。
- Pulse 的 Hub 与 Agent 版本不一致时，页面必须显示双方实际版本、兼容状态和影响范围；仍兼容的基础监控继续运行，不兼容、数据协议变化或可能造成风险的功能暂时禁用，并引导按项目发布规则升级到统一显式版本。不得忽略版本差异冒险操作，也不因可兼容的小版本差异完全停止 Agent。
- Pulse 发现依赖、组件、Hub、Agent 或运行环境存在安全漏洞时，先核对是否实际受影响、严重程度、利用条件和修复版本；确认受影响的高风险漏洞优先在本地完成更新与回归测试，准备备份和回退方案后，再经用户确认更新正式环境。不受影响的漏洞记录判断依据和复查条件，不盲目追新版本，也不拖延已确认的严重风险。
- Pulse 每月主动检查一次 Web、Hub、Agent 及运行环境的依赖更新和已知安全漏洞，正式发布前再针对待发布版本检查一次；记录检查时间、实际版本、是否受影响、处理结论和复查条件。需要联网、安装扫描工具、下载漏洞数据库或升级依赖前，必须取得用户确认。
- Pulse 正式环境的维护、升级、迁移、回滚和其他可能中断家庭使用的操作，每次都要单独确认执行时间；开始前必须用中文说明预计中断时长、受影响功能、备份状态、回退方案和完成后的验收方法。即使版本、镜像和备份已经准备好，也不能在用户未确认当前方便时停止、升级或重启正式服务。
- Pulse 正式维护过程中，如果实际中断时间明显超过预估、发现新风险、需要改变已确认方案，或需要操作原计划之外的数据、服务和配置，必须先停在可恢复的安全状态，保存现场并重新向用户说明影响和选择，取得确认后再继续。原计划内的正常等待可以继续并及时汇报；若存在数据继续损坏或安全风险，先隔离风险再告知用户。
- Pulse 每次正式维护、升级、迁移、回滚或恢复完成后，都要向用户提供中文简短结果报告，写清实际执行内容、实际中断时长、验证结果、异常及处理、观察期状态、剩余风险和需要用户配合的事项；不在报告中堆命令和长日志，关键验收证据在项目记录中脱敏保存。
- Pulse 正式环境故障时，默认最多接受丢失最近 24 小时内的新数据，与每日自动备份频率一致；重要设置变更、版本升级、数据迁移和高风险操作前必须额外创建并验证备份。恢复时优先保住账号、资产、关系、设置和关键记录，并清楚说明可能缺失的数据范围。
- Pulse 正式环境发生严重故障时，目标为尽量在 4 小时内恢复基本使用；优先恢复登录、账号、资产与关系、设备状态查看、告警和必要设置，非关键图表、高级功能和历史整理可以后续恢复。4 小时是恢复目标而非绝对保证；硬件、网络或外部服务造成阻碍时，必须及时说明原因、进度和替代方案。
- Windows Agent 后续采用可安装软件形态：用户通过标准 Windows 安装包完成安装和卸载，安装后由轻量 Windows 后台服务持续采集、连接 Hub、接收网页指令并执行更新；本地只提供按需打开的中文连接配置窗口，不提供托盘程序。关闭窗口后界面进程直接退出，不得停止后台采集。Linux、飞牛、NAS 和 Unraid Agent 继续使用 Docker 形态。
- Windows Agent 安装程序不提供“创建桌面快捷方式”选项，也不得创建桌面图标。安装时必须在开始菜单创建统一的“Pulse Agent”文件夹，文件夹内至少包含“Pulse Agent”和“卸载 Pulse Agent”两个明确入口；Windows 设置中的标准卸载入口也必须保留。
- Windows Agent 安装向导必须提供可编辑的安装位置，不得默认安装到 C 盘。安装器优先选择空间合适的非系统本地固定磁盘，并在目标位置自动创建独立的“Pulse Agent”根文件夹；如果电脑只有 C 盘，或用户主动选择 C 盘，必须在安装位置页面由用户明确确认后才继续。安装前显示目标路径、预计占用空间和可用空间，不自动选择移动盘或网络盘。
- Windows Agent 的程序文件、后台服务程序、连接配置程序、内置采集组件、配置、连接凭据、缓存、日志、下载的更新包和旧版本回退文件统一放在所选“Pulse Agent”根文件夹的明确子目录中，不再把主体数据分散到 `ProgramData` 或系统账户配置目录。连接凭据等秘密子目录必须使用 Windows 文件权限限制访问，不能因为放在可选磁盘而允许普通用户随意读取。Windows 服务注册、卸载登记和开始菜单快捷方式由系统机制保存在 Windows 管理位置，卸载时必须一并清理。
- Windows Agent 必须提供 Windows 设置、开始菜单和安装程序可识别的标准卸载入口。卸载时要可靠停止并删除后台服务和连接配置进程，清理程序文件、开始菜单入口、服务登记、安装器创建的防火墙规则、临时文件和其他由本软件创建的系统项；不能遗留失效服务、进程、快捷方式或自动启动项。连接凭据、本地缓存、日志和用户配置属于数据，必须在卸载界面明确说明并让用户选择保留或彻底删除，高风险删除采用二次确认。
- Windows Agent 卸载时默认彻底删除全部用户数据，包括连接凭据、用户配置、本地缓存和日志；卸载界面必须进行中文二次确认，列出将删除的内容，并明确说明重新安装后需要重新连接。界面可以提供“保留配置以便重新安装”的主动选项，但不得默认勾选；无论是否保留配置，程序、服务、托盘、自启动、快捷方式、安装器创建的防火墙规则和临时文件都必须清理干净。
- 卸载 Windows Agent 只负责彻底清理当前 Windows 电脑，不自动删除 Hub 中对应的设备记录、历史监控和告警；卸载后 Hub 将设备明确标记为离线并保留最后在线时间。确实不再需要该设备时，由管理员在 Pulse 中单独执行删除并进行中文二次确认，避免卸载软件时误删远端历史数据。
- Windows Agent 采用“资产先行、安装后配置”的流程：用户先在 Pulse 资产管理中选择已有的主机资产，系统使用该资产已有的名称和 IP 创建监控接入记录，并为该资产生成一个长期有效且唯一的“机器连接码”；安装程序只负责可靠安装程序文件、后台服务、连接配置程序和开始菜单入口。首次安装成功后只自动打开一次中文连接配置窗口，让用户填写网页提供的 Hub 地址和机器连接码。安装失败与联网或连接码验证失败必须分别提示；配置失败不得破坏已完成的安装。关闭窗口后不再自动打开，后续只能由用户从开始菜单重新进入。
- Windows Agent 首次安装后允许暂时不配置 Hub 并直接关闭连接窗口，不得因此要求重新安装或反复自动弹窗。未配置 Hub 时，后台服务保持已安装和开机自启状态，但只按低频、递增间隔等待配置，不发起无意义的高频连接，也不把“尚未配置连接”误报为连接故障；用户以后从开始菜单打开“Pulse Agent”即可继续配置。
- Windows Agent 完成 Hub 连接后，连接配置窗口必须明确显示“连接成功”和当前 Hub 地址，并只提供“打开 Pulse 网页”和“关闭”两个主要按钮。窗口不得在成功后自动关闭，确保用户能看清结果；点击“打开 Pulse 网页”使用系统默认浏览器打开当前 Hub，点击“关闭”后界面进程直接退出，后台服务继续采集。
- Windows Agent 连接或机器连接码验证失败时必须保留用户填写的 Hub 地址，但本地窗口立即清空连接码输入，不得把失败输入写入本机磁盘、日志或下次打开的窗口。机器连接码由 Pulse 网页在选定资产的监控接入记录中生成，添加过程中和添加完成后都可由有权限的管理员查看和复制；本地窗口不提供生成、重置或复制入口。界面区分显示“地址无法访问”“机器连接码错误”“机器连接码已被重置”等真实原因，并提供“重试”和“关闭”按钮。
- Windows Agent 已完成连接后，用户从开始菜单再次打开连接配置窗口时，默认显示“已连接”、当前 Hub 地址，并提供“打开 Pulse 网页”“重新配置连接”和“关闭”三个主要按钮。重新配置必须输入新的 Hub 地址和对应资产的机器连接码，先验证目标 Hub 和连接码，再用中文二次确认替换当前连接；只有新连接完整验证成功后才原子保存并切换，任何失败都继续使用原有连接，不得产生重复设备、丢失旧凭据或留下半配置状态。
- 已连接状态下当前 Hub 地址只读显示，不允许直接在原位置修改；只有点击“重新配置连接”并取得编辑权后，才显示可编辑的新 Hub 地址和机器连接码输入区域。取消、验证失败或未通过二次确认时继续使用原连接，不覆盖原地址或凭据。
- 进入“重新配置连接”后，先显示中文提醒：“验证成功并确认后，旧连接会被替换；验证失败不会影响当前连接。”用户在提醒下继续填写新地址和机器连接码；未完成验证和二次确认前，旧连接持续生效。
- 重新配置提醒必须由用户点击“我知道了”确认后，才显示或启用新的 Hub 地址和机器连接码输入区域；在确认前不能提交、验证或修改原连接。
- 重新配置时用户填写新地址和机器连接码后，先点击“验证新连接”；只有验证成功，才显示最终替换确认。验证失败只显示真实中文原因并保留旧连接继续工作，不修改原地址、凭据或后台服务。
- 验证新连接成功后，最终确认按钮文字固定为“确认替换连接”，按钮旁再次显示“旧连接将在确认后失效”。只有用户点击该按钮后才原子替换连接；取消则继续使用旧连接。
- 执行连接替换时显示“正在切换连接”，暂时禁用关闭、返回和重复点击，避免留下半配置状态；切换完成并确认后台服务使用新连接后显示“连接已更新”，再恢复可操作状态。
- 如果连接切换失败，显示“连接切换失败，仍在使用旧连接”，明确旧连接继续生效，并提供“重试切换”和“返回”两个按钮；重试前保留新地址与机器连接码输入但不得覆盖旧配置，返回则放弃本次新连接。
- 连接切换失败后点击“返回”必须先显示确认：“确定放弃本次连接切换吗？”选择继续切换时保留新地址和机器连接码，确认放弃后才清空新输入并回到旧连接状态；旧连接在整个过程中继续生效。
- 机器连接码由 Pulse 网页绑定到资产管理中选定的机器资产并长期保留；在“资产监控”页面点击“添加监控”后，先在当前添加页面填写和确认机器信息，不立即生成连接码，也不跳转到其他页面。只有点击“确认添加”并成功创建监控接入记录后，才为没有连接码的资产生成唯一机器连接码并直接显示；重复打开或取消添加不会生成新码，已有连接码的资产继续使用原码。添加过程中和添加完成后，网页接入记录都向管理员直接显示完整机器连接码，不使用星号遮挡，也不提供额外的查看 / 隐藏入口。管理员可以点击“复制机器连接码”，复制到剪贴板的始终是完整连接码。只有管理员可以查看或复制完整连接码；复制成功提示“机器连接码已复制”，失败提示“复制失败，请手动选择连接码复制”。复制动作必须记录操作人、时间和对应资产，但操作审计不得保存连接码原文。管理员还可主动“重置机器连接码”；点击后先显示影响说明：“重置后，旧机器连接码立即失效；已保存的现有连接继续按当前状态运行，之后重新安装或重新配置必须使用新连接码。”确认弹窗只提供“取消”和“确认重置”两个按钮，不要求输入机器名称或固定文字；确认后立即生成并显示新的机器连接码，旧码不再显示，同时短暂提示“机器连接码已重置”，提示几秒后自动消失，并记录重置时间和操作人。Windows 本地重新配置窗口不显示有效期或提供重置入口；输入失效连接码只清空本地新输入，不修改旧地址、旧凭据或后台服务。
- 每台资产同一时间只能有一条有效的监控接入记录。已经存在接入记录的资产不再出现在“添加监控”的可选机器列表中；即使尚未连接成功或机器连接码生成失败，也必须回到原记录继续生成、复制、重置连接码或查看状态，不得重复添加。需要重新接入时复用原记录并重置机器连接码或重新配置连接，不创建第二条记录，避免重复机器、重复数据和重复告警。
- 管理员可以在资产监控记录中主动“删除监控目标”。这是高风险操作，点击后必须进行中文二次确认，弹窗直接提示：“删除后会删除该监控目标的所有历史记录，包括历史指标、历史告警和其他监控数据，且无法恢复。”同时明确不会删除资产资料或删除操作审计；确认按钮为“取消”和“确认删除监控目标”。确认后立即停止接受该 Agent 的新数据，使当前机器连接码和已经发放的连接凭据失效，并把该资产重新放回“添加监控”的可选列表。删除完成后不保留这段监控的历史数据；以后重新添加时创建新的有效接入关系、新机器连接码和全新的数据时间线，不恢复已经失效的旧凭据。
- 取消监控后，如果原 Agent 仍继续上报，Hub 必须直接拒绝本次上报，不保存新监控数据；Agent 收到“当前监控已取消”的结果。拒绝事件写入系统日志和必要的操作记录，但不得反复弹窗或重复通知用户。只有管理员重新添加该资产并生成新的机器连接码后，Agent 才能恢复接入。
- Windows Agent 收到“当前监控已取消”后，本地连接窗口必须明确显示同名状态，不得显示为普通“连接失败”或网络故障。后台服务继续保持已安装和开机自启，但停止正常数据上报，只进行低频连接状态检查，避免反复请求和资源浪费；本地保留原连接配置用于排查，不自动清除。窗口提供“打开 Pulse 网页”“重新配置连接”和“关闭”；管理员重新添加资产并生成新的机器连接码后，通过“重新配置连接”完成验证并恢复接入。

- Windows Agent 安装器必须把开始菜单中的“Pulse Agent”文件夹和配置入口创建为本机所有登录账号可见，而不是只属于执行安装的账号。任一已登录账号都可用普通用户权限打开窗口，查看这台电脑共用的后台服务状态、当前 Hub 地址和连接状态；不得向普通账号显示连接凭据或其他秘密值。首次保存连接或重新配置 Hub 仍按管理员权限规则执行，连接配置对整台电脑生效，不为不同 Windows 账号建立互相冲突的独立连接。配置窗口单实例范围按当前登录会话处理，不跨 Windows 会话强行切换其他账号桌面上的窗口。

- Windows Agent 的采集开关采用逐项独立控制，安装后默认全开，不提供额外的一键全开按钮。温度、GPU、Docker 和各类特殊硬件能力分别显示当前状态、采集收益、所需依赖、权限要求和预计资源影响；用户可以单独关闭某一项，关闭时只停止该项后台任务，不影响其他采集。依赖缺失或设备不支持时，对应项目显示“不可用”及中文原因与下一步。
- Windows Agent 的日志、诊断摘要与技术详情统一在 Pulse 网页展示，默认使用中文摘要并按需展开技术详情；显示、复制与导出内容必须隐藏 Token、连接凭据和其他秘密信息。本地连接窗口不提供日志浏览、日志目录或诊断管理入口。
- Windows Agent 更新只能从 Pulse 网页发起，不在本地连接窗口提供检查更新或“立即更新”按钮。网页发现新版本时显示版本号、中文更新内容、预计影响和是否需要重启服务；管理员二次确认后才由 Hub 下发任务。更新失败时继续使用或自动恢复旧版本，不得留下半更新状态；确需回退时走单独恢复流程并再次确认。
- Windows Agent 的版本信息和更新包统一通过当前已连接并认证的 Pulse Hub 获取，Agent 不直接连接 GitHub 或其他公开发布站点。Hub 负责向已认证 Agent 提供管理员允许安装的版本、中文更新说明、更新包和校验信息；Agent 下载后仍须独立验证版本、文件完整性和发布可信性，校验失败不得安装。Hub 暂时不可用时继续运行当前版本并显示中文原因，不影响现有采集。
- Windows Agent 更新以 Pulse 网页为唯一入口：管理员在网页选择具体设备并点击更新，中文二次确认后由 Hub 向该设备下发更新任务；网页持续显示准备、下载、校验、安装、服务重启、重新连接和最终结果，并统一记录失败回退与操作审计。
- Pulse 每次开发完成后只保存关键验证结果，包括执行的测试与检查、通过或失败结论、页面实查结果、未覆盖范围和剩余风险；普通开发不保存大段无用日志。正式发布、数据迁移、认证权限、备份恢复和部署等高风险阶段应保存更完整且经过脱敏的验收证据，证据不得包含密码、Token 或其他秘密信息。
- Pulse 网页采用电脑优先、手机可用的响应式策略：复杂设备管理、网络拓扑和系统设置主要保证电脑端效率；手机端重点保证设备状态查看、告警接收与处理和日常事项操作。界面改动必须检查主要桌面与手机尺寸下的文字、按钮、表格、弹窗、触控和异常状态，不因暂时暂停 Android 开发而放弃手机网页体验。
- Pulse 对删除数据、远程控制、批量修改、恢复备份、覆盖配置和重启服务等高风险操作采用二次确认：确认界面必须用中文说明操作对象、影响范围、备份或回退方法和不可逆风险，用户明确确认后才允许执行；普通查看、筛选和非关键备注编辑不增加不必要的确认。
- 开发工具、SDK 和缓存不得安装进 Pulse 项目目录。

## 维护方式

- 本文件只维护 Pulse 专属规则。
- 通用沟通、工具自动选择、安装确认、方案确认和用户配合说明，维护在 Codex 用户目录的全局规则文件中。
- 迁移到新电脑时，只复制当前用户 Codex 目录下的 `global-guidance` 文件夹即可带走通用规则；本项目目录中的本文件只随 Pulse 项目一起复制。
- 删除或新增通用规则时，修改全局文件；删除或新增 Pulse 专属规则时，修改本文件。两者不要互相复制，避免不同项目之间串规则。
